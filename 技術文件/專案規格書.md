## 第一部分：系統核心原則

### 1. 來源資料不可侵犯鐵律（沿用 V1.0.0，未變動）

全系統的清理、搬遷、改名、去重與最佳化操作，僅作用於系統管轄的沙盒副本目的地，絕不對使用者原始來源地（手機相簿、SD卡、外接硬碟等）進行任何寫入、截斷或刪除。

### 2. 原始畫質永久保留原則（V2.0.0 新增，本版最核心的架構決策）

**決策**：**匯入時原始檔案直接複製進整理夾，完全不經過任何壓縮或縮放處理**。整理夾裡的每一個實體檔案，永遠是使用者原始素材的位元組級複本。

**配套機制**：
- `Mod_Utils.CopyPhysicalFile` 複製完成後核對來源與目的地檔案大小是否一致，不一致視為複製失敗，刪除半成品並報錯，不允許損毀或不完整的複本冒充匯入成功。
- 畫布嵌入需求（見下一條原則）改為另外產生縮圖，不動用整理夾本體。

### 3. 雙軌畫質分流原則（V2.0.0 新增）

一張圖片自匯入起，在系統中永遠存在**兩份物理上獨立的資料**：

| | 整理夾原始檔案 | 畫布縮圖快取 |
|---|---|---|
| 畫質 | 完整、未經任何處理 | 固定壓縮至 `cls_Config.ThumbnailCacheDimension`（預設1920） |
| 儲存位置 | `圖片整理夾`（或其子夾） | `圖片整理夾\.縮圖快取\`（透過 `Mod_Utils.SetFolderHidden` 設定 Windows 隱藏屬性，非僅檔名前綴句點） |
| 用途 | 匯出高畫質成品、保存原始素材 | 嵌入 Excel 畫布顯示、控制活頁簿檔案體積 |
| 使用者是否可調整畫質 | 不可，永遠原始 | 不可，固定值，介面上的寬度設定僅控制**顯示縮放**，與縮圖實際解析度無關 |

**這個分流解決的核心矛盾**：Excel 的 `Shapes.AddPicture`（`SaveWithDocument:=msoTrue`）會把來源檔案的完整資料嵌入活頁簿本身，若直接嵌入原始大圖，活頁簿檔案體積與 GDI 渲染負擔會迅速失控（已知的「180張以上當機風險」即源於此）。分流後，畫布只嵌入縮圖，活頁簿體積可控；整理夾保留原始檔案，畫質訴求同時被滿足。

**已知限制**：使用者若手動刪除整理夾裡的原始檔案，畫布上的縮圖依然正常顯示、不會有任何異狀，直到下一次匯入或全面排版才會被偵測為「實體遺失」；若此時選擇救援，只能用縮圖畫質重新存檔，原始畫質從此無法復原。此風險已寫入 README 警告一（詳見第九部分）。

### 4. 身分辨識雜湊化原則（V2.0.0 新增，全系統影響範圍最大的一次重構，見 ADR V2-009）

**決策**：**判斷「這是不是同一張圖」的唯一依據是內容雜湊值（MD5），檔名永遠只是顯示用途，不參與任何身分判斷邏輯。**

**落地方式**：
- `Mod_StateScanner.ScanCurrentState` 的存活清單（`dictOrgAlive`／`dictRescueAlive`）鍵值改為雜湊，不再是檔名。
- 畫布 Shape 是否遺失的判斷：先透過目錄表建立的「名稱→雜湊」對照表，把 Shape 名稱轉換成雜湊，再去查存活清單。若 Shape 名稱在目錄表裡完全查無記錄（例如手動貼上的野生截圖），一律視為遺失，導入既有救援流程，順便正式登記進目錄表。
- `cmd_Rebuild.ProcessSingleFile` 的「這個實體檔案是否已經掛上畫布」判斷（`alreadyHasShape`），改用雜湊反查表（`m_DictHashToShape`，雜湊→工作表||Shape名稱），達成 O(1) 查詢，不再逐一巡邏 Shape 集合或依賴 `wsImg.Shapes(檔名)` 這種名稱索引。
- `cmd_Rebuild.CleanInvalidShapes`（排版收尾清除失效圖形）同步改為透過雜湊比對，不再直接用 Shape 名稱查詢。

### 5. 旗幟命名機制（V2.1.0 修訂：雜湊尾巴改用明確標記，見 ADR V2-022）

**目的**：在「身分判斷不依賴檔名」的前提下，檔名本身仍然需要保證**實體層級的唯一性**（Windows 檔案系統、Excel Shape 名稱皆要求同層級不可重複），旗幟命名機制負責這件事。

**格式**：`原始檔名_HASH雜湊前8碼.副檔名`（例如 `IMG_0042_HASHa1b2c3d4.jpg`）

**V2.1.0 變更說明**：舊格式僅以「結尾8碼、全部是十六進位字元」判斷是否為系統雜湊尾巴，此特徵並非唯一，若使用者原始檔名恰好符合此樣式（如特定相機命名慣例），有極低機率被誤判、誤拔除。新格式明確要求 `_HASH` 四字元前綴，消除此誤判空間。`Mod_Utils.StripHashSuffix` 為全系統唯一負責拔除此尾巴的函式，僅認得新格式，舊格式資料不會被正確拔除（見第八部分已知限制）。

**適用範圍**：整理夾內所有透過系統匯入或排版時新發現的圖片，實體檔名與目錄表第1欄（識別名稱）、畫布 Shape 名稱三者統一採用此格式，且此三者現在保證**完全同步**（見「實體同步」機制，第四部分 `cmd_Rebuild`）。

**與顯示名稱的分工**：目錄表另有第11欄「顯示名稱」，由 `cmd_Rebuild` 寫入目錄列時，透過 `Mod_Utils.StripHashSuffix` 拔除雜湊尾巴計算得出，純粹給使用者瀏覽用，不參與任何比對邏輯。

**與救援烙印命名的關係（V2.1.0 修訂：烙印格式簡化，見 ADR V2-024）**：`cmd_Rescue` 產生的救援檔名格式簡化為固定字串 `MANUAL_RESCUE_旗幟識別名稱`（**不再內嵌日期**，日期資訊已完整記錄於目錄表「登錄時間」欄位，烙印裡的日期屬於重複資訊且讓拔除邏輯更脆弱）。`Mod_Utils.ExtractOriginalIdentifier` 負責拔除此固定長度前綴（14字元）還原旗幟識別名稱，改用 `Left`／`Mid` 固定長度比對，不再依賴底線分段計數。此函式並改為**迴圈拔除**（見 ADR V2-023），可正確處理理論上可能出現的巢狀烙印（套娃），非僅拔除單層。

**「何時該拔除烙印／雜湊尾巴」的統一原則（V2.1.0 新增，見 ADR V2-025）**：全系統僅有兩處會呼叫 `ExtractOriginalIdentifier`：`cmd_Deduplicate.ApplyFileMatch`（身分真正確定、正式取代救援紀錄的正名時刻）、`cmd_Import.DetermineFinalName`（撞名詢問已有明確決策、為新圖片計算乾淨命名的時刻）。**任何比對／偵測階段（撞名詢問偵測本身）一律使用完整原始字串比對，不預先做任何拔除**——此原則是 V2-021（無聲取代漏洞）修復後確立的鐵律，偵測階段判斷基準若比詢問更寬鬆，會重新製造出繞過確認的後門。

### 6. 軟體工程金律與大批次持久化（沿用 V1.0.0，V2.2.0 補充例外，見 ADR V2-045）

SOLID、DRY、KISS、YAGNI 原則不變。批次防線原則上維持「每20筆回報進度、每60筆存檔」的既有節奏，**但此節奏並非無條件套用於所有逐項迴圈**——是否需要頻繁中途存檔，取決於該迴圈是否觸發COM剪貼簿瞬斷風險、以及中途崩潰造成的落差有無自動追平機制，完整判準見第四部分第9節「批次存檔適用範圍分界原則」。

### 7. SSOT 絕對資料疆界（沿用並擴充）

三大既有領地（`cls_Config`／`cls_StringLibrary`／`cls_ExecutionContext`）不變。V2.0.0 額外強調：**任何新增的資料夾路徑，一律收斂進 `cls_Config`，禁止在任何呼叫端寫死中文資料夾名稱字面值**——本版新增的四個資料夾（散裝個別匯入、雜湊衝突軟刪除匯入圖片、雜湊衝突淘汰救援圖片、縮圖快取）皆遵循此規則，經全域搜尋確認零殘留字面值。

**V2.1.0 補充**：本輪 SSOT 稽核延伸至操作介面儲存格位址與數值邊界，`cls_Config` 新增 `CellImgWidth`／`CellImgSpacing`／`CellNamingMode`／`CellSheetPrefix`／`CellPdfImgName`／`CellPdfCatName`／`CellPdfGrid`／`CellExportFilter`／`CellExportRange` 等九個儲存格位址屬性，以及 `MinImgWidth`／`MaxImgWidth`／`MinImgSpacing`／`MaxImgSpacing` 四個數值邊界屬性。**寬度／間距上限 `1333` 並非拍腦袋數字，是由 Excel 欄寬硬上限（254）反推的精確數學邊界**（`254 × 5.25 = 1333.5`），超過此值會導致 `cmd_Rebuild` 排版時欄寬跟不上圖片實際寬度，圖片溢出欄位範圍，是此前「寬度設定過大會當機」問題的根本數學原因。此輪稽核亦發現並刪除一個死碼屬性（`CellAutoLayoutStateFlagSet`，與 `CellAutoLayoutStateConsole` 同指向 Z1 卻從未被任何程式碼讀取）與一個真實重複屬性（`CellFormatBehaviorFlagSet`，已與 `CellDangerConsole` 合併）。

### 8. 自訂表單邊界原則（V2.3.0 新增，見 ADR V2-099）

**定義**：工作表名稱以 `cls_Config.PrefixCustom`（`###`）開頭者，視為使用者自主管理的自訂表單。

**保證**：自訂表單**保證不受任何自動化流程影響**——不受排版引擎管轄（`Mod_Rules.IsStandardImgSheet` 明確排除，不會被 `ExecuteMasonryLayout` 或 `CleanInvalidShapes` 觸碰）、不受全域鎖定自動上鎖（`EnforceStandardSecurityState` 與 `ToggleGlobalLock` 上鎖分支皆排除自訂表單）、執行【全面排版】後仍會收到導覽按鈕自動注入（與標準圖片表享有同等待遇，但不受其餘排版規則管轄）。

**V2.3.0 修正說明**：此原則本為既有說明書承諾，但稽核發現全域鎖定與導覽按鈕注入兩處實作皆未真正落實排除自訂表單——本版屬於補齊既有承諾與程式碼實際行為的落差，非新增保證範圍。

**V2.1.0 移除說明**：圖片母夾根目錄散落檔案自動收編機制已整體移除（見 ADR V2-026）。系統不再主動偵測或處理直接放置於圖片母夾根目錄的檔案，母夾自此僅作為容器層級存在，不承載任何業務邏輯。

**V2.2.0 拓樸調整說明**：原「雜物垃圾／備份快照」語意上把備份這種有價值的安全網資料歸類在垃圾底下，並不精確。新增「封存備份」獨立柱後，「雜物垃圾」柱僅保留隔離區，備份快照與新增的日誌封存皆移至「封存備份」柱下統一管理，行為本身無變化，純粹是分類歸屬調整（見 ADR V2-040）。

| D (4) | 檔案大小 | | 否 |
| E (5) | 登錄時間 | | 否 |
| F (6) | 檔案修改時間 | | 否 |
| G (7) | 管線執行狀態 | 例如「已歸位」「系統救援」 | 否 |
| H (8) | 是否觸發救援 | 「是」代表目前處於等待救援中狀態（isBounty） | 是，決定該筆是否進入候選比對名單 |
| I (9) | 原始HASH | 永久錨點，第一次登記後除非明確判定「取代舊血統」否則不再變動 | 是，核心判斷依據 |
| J (10) | 實體狀態 | 例如「檔案正常」 | 否 |
| K (11) | 顯示名稱 | `StripHashSuffix` 計算得出，純顯示用途 | 否，禁止參與任何比對 |

### 第2欄與第9欄的分工原則

- **第2欄（目前HASH）**：永遠反映「這一列現在對應的實體，內容雜湊是多少」，每次身分轉移（救援、取代、正名）都會被覆寫。
- **第9欄（原始HASH）**：血統錨點。原則上第一次登記後永久不變（`If origHash = "" Then origHash = currHash`）；**唯一的例外**是「同名不同HASH，使用者明確選擇取代」的情境——此時第9欄要跟著重置為新檔案自己的雜湊，代表舊血統正式終結、新血統從此刻重新起算，避免舊的原始HASH繼續在雜湊比對中製造混淆。「原始圖片回歸」情境（新檔案雜湊等於第9欄既有值）則第9欄維持不變，因為新舊本來就是同一條血統。

## 第四部分：核心行為與命令物件職責

### 1. `cmd_Import`（見 ADR V2-017系列）

命名邏輯（`DetermineFinalName`）與歸檔路徑邏輯（`DetermineFinalFolder`）解耦，六種命名模式（原始名稱／今日日期／修改日期／自訂前綴／自訂_今天日期／自訂_修改日期）可與任一來源類型自由組合。

- `ImportSingleFileViaSandbox`：複製進 `.暫存區`（固定檔名）→ 決定正式命名與位置 → 複製到正式位置＋核對檔案大小 → 核對通過才刪除暫存殘留。
- 批次內部去重（`dictBatchHash`）僅比對本批次彼此，不查整理夾既有內容（交由 `cmd_Deduplicate` 處理）；批次查重用 `GetSmartHash`（超過50MB用替代識別值），圖片命名雜湊用真 `GetMD5`（`trueImageHash`），兩者刻意不同（見ADR V2-091）。
- 路徑防護：保護清單由 `config` 動態組成，比對用 `Left` 路徑開頭比對（ADR V2-073）。
- 命名前先執行複製尾巴／括號流水號清洗，直接丟棄（ADR V2-102）。
- 單檔案失敗僅記錄日誌，不影響同批次其餘檔案。
- 「散裝個別匯入」資料夾（`config.IOLooseImportFolder`）：個別選檔匯入落入此處，目的是簡化 `cmd_Rebuild` 分表判斷，非防撞名（ADR V2-013）。
- 母夾定位：`圖片母夾`（`config.IOTargetFolder`）是純容器層級，不參與雜湊掃描／去重／排版；只認得底下「圖片整理夾」「救援夾」兩個具名子資料夾，根目錄檔案系統忽略。

### 2. `Mod_ImportCollisionGate`（撞名蒐集與詢問統一入口，見 ADR V2-025~028）

`GatherConflicts`（蒐集，不彈窗）→ `AskAndApplyDecisions`（一次性彈窗，套用決策）。

- `opMode="IMPORT"` 比對範圍為選取檔案；`"REBUILD"` 比對整理夾現有全部檔案。
- 比對用完整原始字串，不預先拔除烙印或雜湊尾巴（ADR V2-025）。
- 呼叫順序：`Mod_Pipeline.Run` 於 IMPORT 時呼叫 `GatherConflicts`；`cmd_Rebuild` 開頭呼叫 `GatherConflicts("REBUILD")` 接續 `AskAndApplyDecisions`，確保匯入接排版全程只彈窗一次（ADR V2-028）。
- 選「是」：目錄列標記「已取代」，舊救援殘影歸檔至已歸位圖片（讀目錄表第3欄實際路徑，非命名規則猜測，ADR V2-100）。

### 3. `cmd_Deduplicate`（見 ADR V2-019~021）

現無任何可繞過使用者確認、直接完成身分取代的路徑。

- 候選比對：原始HASH＞救援HASH優先權；`OrigHash` 候選不限 `isBounty` 狀態，`RescueHash` 候選限 `isBounty=是`（ADR V2-082）。
- 雜湊來源：步驟3用真 `GetMD5`（ADR V2-091）。
- 正名（`ApplyFileMatch`）：拔烙印還原識別名稱；同名不同HASH取代重置第9欄血統錨點；取代前若舊路徑（第3欄）存在且不同，先行歸檔（ADR V2-100）。
- 雙軌軟刪除：一般重複 → `IODuplicateDiscardFolder`；救援候選落敗 → `IORescueDiscardFolder`。附件重複獨立搬入 `IOAttachmentDuplicateDiscardFolder`（ADR V2-046）。
- 雜湊重用：`cls_ExecutionContext.DictPathToHash` 正向索引，避免同一管線內圖片雜湊重算兩次（ADR V2-047）。

### 4. `cmd_Rescue`（畫布資產急救，見 ADR V2-038、V2-052～V2-063）

掃描 `Context.MissingShapes`，逐一截圖存至救援夾；找不到目錄列則新增。命名：`MANUAL_RESCUE_旗幟識別名稱`。

- `StartGdiplusEngine`／`StopGdiplusEngine` 由呼叫端在批次迴圈外各自啟停一次（ADR V2-052）。
- 擷取尺寸固定為 `config.MaxSafetyPoint`（1440pt，ADR V2-061）。
- 圖形搬移：PNG存檔成功後 `AddPicture` 嵌入新圖，確認成功才刪除原Shape（複製優先於刪除）；失敗則原圖形保留、可重新觸發救援（ADR V2-054、V2-057）。
- 救援夾嵌入固定寬度 `config.RescueEmbedWidth`（300pt），垂直堆疊間距 `config.RescueEmbedGap`（50pt，ADR V2-062、V2-063）。
- `Context.SessionRescued` 於搬移確認成功後才計入。
- 存檔頻率 `Mod 300` 一次；`Mod_Actions.ExecuteProactiveRescueAndSnapshot`（象限3緊急搶救）另補 `Mod 60` 存檔＋複製優先於刪除保護（ADR V2-067、V2-084）。

### 5. `Mod_ThumbnailCache`（見 ADR V2-077）

- `GetOrCreateCachedPreview`：同名快取存在則回傳，否則產生；失敗降級回傳原始檔案路徑。
- `CleanOrphanedCache`：遞迴掃描整理夾＋救援夾建立有效檔名清單，比對快取資料夾清孤兒。

### 5a. `Mod_FilenameNormalizer`（獨立應急工具，見 ADR V2-065、V2-081）

零參數 `修改流水號格式()`（`Alt+F8`）：選資料夾 → Dry Run預覽 → 確認 → 執行。供保留原始編號需求時手動使用，與自動觸發並行、非替代關係。

### 5b. `Mod_EmptyFolderCleaner`（見 ADR V2-089）

零參數 `清除空資料夾()`（`Alt+F8`），範圍限 `config.IOOrganizeFolder`，由下往上遞迴，系統管理資料夾一律排除（依 `Mod_Actions.GetAllManagedFolderPaths` 判斷）。全面排版結尾自動呼叫（`dryRun=False`）。

### 6. `cmd_Rebuild`（見 ADR V2-017、V2-044、V2-068、V2-069）

```
BackupCatalogState（清空前備份，含 m_DictDNA 血統延續）
→ ConsolidateLooseFilesInOrganizeRoot
→ GatherConflicts("REBUILD") + AskAndApplyDecisions
→ CleanUpOldSheets
→ 建立 Shape 雜湊索引（m_DictShapeHash/m_DictHashToShape，讀 BackupCatalogState
   保存的舊資料，早於 InitializeCatalogSheet，ADR V2-017、V2-098）
→ InitializeCatalogSheet（清空重建）
→ 逐檔 ProcessSingleFile
```

- `ProcessSingleFile`：查 `m_DictHashToShape`，已掛載跳過；未掛載則 `GetOrCreateCachedPreview`＋`AddPicture`；非救援檔案做實體同步（改乾淨旗幟名稱，複製核對後刪舊檔）；救援檔案優先沿用 `m_DictDNA` 血統名稱。
- Shape名稱同步：比對 `shp.Parent.Name` 與目標工作表是否相同，相同原地改名，不同走完整搬移（複製優先於刪除，ADR V2-074、V2-086）。
- `CleanInvalidShapes`（孤兒清除，排版前執行，ADR V2-097）：刪除前查 `isBounty` 狀態，等待救援中的圖形不視為孤兒（ADR V2-068）；刪除前記錄完整診斷資訊（ADR V2-087）。
- 分表依據：資料夾合併模式用 `GetTopLevelFolderName`；同名合併模式用清乾淨雜湊尾巴前的名稱分組（`cleanedNameBeforeHash`，ADR V2-064）。雜湊尾巴分隔符號為 `_#HASH`（ADR V2-066）。
- 雜湊快取日期格式統一為 `Format(x, "yyyy/mm/dd hh:mm:ss")`（ADR V2-069）。
- 複製尾巴／括號流水號：交錯呼叫 `StripTrailingParenNumber` 與 `StripKnownCopySuffix`，直接丟棄（安全上限30輪，ADR V2-102）。
- 雜湊計算一致性：永久身分用途一律真 `GetMD5`；一次性判斷用途可用 `GetSmartHash`（ADR V2-091）。
- 嵌入畫布來源：`AddPicture` 讀縮圖快取；救援夾檔案固定寬度 `config.RescueEmbedWidth`，非救援檔案用 `Context.DynamicImgWidth`；`ExecuteMasonryLayout` 排版時對救援表同樣套用固定尺寸，不受一般動態設定影響。
- **局部重排**（ADR V2-094～V2-096）：操作介面 B6:B8 三格 `Locked` 屬性為鎖定狀態唯一事實來源；`m_DictTouchedSheets` 標記本輪被摸過的工作表；鎖定時只重排有標記的表。確認彈窗合併進REBUILD既有Pre-Flight Check，不獨立彈窗。按鈕採「開／關」語意，儲存格採「鎖／可編輯」語意，刻意相反。自訂表單不受影響。
- 空資料夾清理：結尾自動呼叫 `ScanAndRemoveEmptyFolders`（ADR V2-089）。

### 7. `Mod_Bootstrap`（系統骨架自救模組）

`主動初始化`、`主動重繪UI`、`強制統一密碼` 三個零參數 `Public Sub`。`FORBIDDEN` 條款明文禁止任何進入點加參數，見 ADR V2-003。

### 8. 「自動排版」開關職責邊界（見 ADR V2-029）

唯一職責：使用者未按按鈕、單純改操作介面設定時，系統是否主動反應排版（邏輯位於 `工作表1.cls` 的 `Worksheet_Change`）。按鈕觸發的操作（開始作業／全面排版／預覽排版）不受此開關影響。開關狀態僅能被使用者手動變更或初始化預設值改變，不會被排版操作自動覆寫。

### 9. 批次防線三層防護分級設計（見 ADR V2-032、V2-033）

**核心原則**：先問「這是不是逐項迴圈」「迴圈裡有沒有操作佔用剪貼簿等系統層級共享資源」，兩者答案決定頻率設計，不可一概而論。

1. **換氣＋斷點存檔**：逐項迴圈皆須具備，每20筆回報進度、每60筆存檔。
2. **資源釋放**：僅適用於呼叫 `CopyPicture`／`Copy`／`Paste` 的迴圈，每次操作完成後立即清空剪貼簿（`Application.CutCopyMode = False` ＋ `CreateObject("htmlfile")`），不沿用60筆存檔頻率。
3. **單項目錯誤隔離**：任一項目失敗只記錄日誌、跳過，不影響同批次其餘項目。

**全系統覆蓋現況**：

| 位置 | 逐項迴圈 | 換氣＋斷點存檔 | 資源釋放 |
|---|---|---|---|
| `cmd_Import`（匯入） | 是 | 是 | 不需要 |
| `cmd_Rebuild`（排版） | 是 | 是 | 不需要 |
| `cmd_Deduplicate`（雜湊計算階段） | 是 | 否，命令結束後統一存一次 | 不需要 |
| `cmd_Deduplicate`（第二／三輪比對） | 是 | 否，同上 | 不需要 |
| `cmd_Rescue`（救援） | 是 | 是 | **是，每次** |
| `Mod_Export` 畫布優先（主路徑：剪貼簿） | 是 | 是 | **是，每次** |
| `Mod_Export` 畫布優先（降級：暫存檔） | 是 | 是 | 不需要 |
| `Mod_Export` 資料夾直匯（主路徑：`AddPicture`） | 是 | 是 | 不需要 |
| `Mod_Export` 資料夾直匯（降級：剪貼簿） | 是 | 是 | **是，每次**（ADR V2-036） |
| `Mod_Export` 直接變成PDF模式 | 否，單次API呼叫 | 不適用 | 不適用 |

**批次存檔適用範圍**（ADR V2-045）：兩前提同時成立時（① 觸發COM剪貼簿瞬斷風險 ② 有「下一次操作自動追平」機制），改為命令結束後統一存一次，非逐批存檔。`cmd_Rescue`、`Mod_Export` 剪貼簿路徑因有真實COM瞬斷事故紀錄，不適用，維持頻繁存檔。

### 10. `cls_Log` 日誌治理機制（見 ADR V2-041、V2-042、V2-070）

- `ArchiveAndTrim`：超過3000列時，除最新500列外寫出CSV至封存備份，複製優先於刪除；觸發於 `BootSystem` 非危險區分支，另有 `Mod_Bootstrap.封存並清除系統日誌` 手動入口。
- `RevealLogSheet`／`HideLogSheet`：切換 `Visible` 前需先解除活頁簿結構鎖（`wb.ProtectStructure`），比照 `重建操作介面` 自癒前置手法。
- `ValidateLogSheetCache` 共用私有程序：解決 VBA 物件變數指向已刪除工作表不會自動變 `Nothing` 的問題，`Record` 與 `LocateLogSheetIfNeeded` 皆呼叫此程序。

### 3. 身分核對與軟刪除去重拓樸（Deduplicate Pipeline，V2.1.0 更新：移除第一輪，見ADR V2-021）

```
[cls_DAGEngine] → [cmd_Deduplicate] (ICommand_Execute)
   │ 1. 讀目錄表，篩出 isBounty=True (等待救援中) 的候選紀錄
   │    建立兩份候選字典（V2.1.0起僅存兩份，原第一輪m_DictCandidateName已整段移除）：
```

## 第八部分：已知限制與未解決事項

以下項目已識別但刻意保留現狀，非遺漏：

1. **整理夾原始檔案遭手動刪除的風險**：雙軌畫質分流下，畫布縮圖獨立於原始檔案存在，刪除原始檔案不會立即顯示任何異狀，只有下次匯入或全面排版才會被偵測。已透過 README 警告一因應，未在程式層面加入額外攔截。
2. **複製後完整性核對僅比對檔案大小，非逐位元組雜湊比對**：`CopyPhysicalFile` 為了效能考量未做逐位元組核對，理論上無法排除「大小相同、內容不同」的極端邊界案例。
3. **雜湊尾巴新舊格式不相容**：V2.1.0 改用 `_HASH` 明確標記後，此前產生的舊格式雜湊尾巴（純8碼十六進位、無標記）無法被新版 `StripHashSuffix` 正確識別拔除，可能與新格式疊加產生視覺上混亂但功能無害的殘留字串。建議舊測試資料清空重測，不強求向後相容。
4. **舊格式救援烙印殘留資料**：`ExtractOriginalIdentifier` 對於烙印格式簡化前（含日期）產生的舊資料，因固定長度拔除邏輯與舊格式段落數不符，可能無法完全拔淨，殘留日期片段。
5. **手動改整理夾檔名可能造成目錄表短暫不一致，但目前無實測證據支持風險真實存在**：`cmd_Rebuild.ProcessSingleFile` 現已具備「格式統一+實體同步」機制（見第四部分第6節），會主動將實體檔名同步回正確的旗幟格式，此前擔心的「目錄表產生重複列」風險理論上已大幅降低，但尚未經過刻意設計的對照實驗完整驗證，狀態標記為「觀察中」而非「已解決」。
6. **`AskAndApplyDecisions` 若匯入後未觸發任何排版**：`Context.PendingConflicts` 蒐集到的衝突會持續保留，直到下次任何操作觸發 `REBUILD` 的蒐集/詢問流程才會被處理，此為刻意接受的行為，非缺陷。
7. **救援失敗清單可直接查閱，但仍非獨立可視化清單（V2.2.0部分解決）**：`cmd_Rescue` 單項目錯誤隔離（V2.1.1新增）會將失敗原因記入日誌，V2.2.0起操作台新增【系統日誌】按鈕，使用者可自行點按顯示/隱藏日誌工作表，不再需要另外請人協助查閱（見第四部分第10節）。但呈現方式仍是原始日誌全表，未做成篩選過「僅顯示失敗項目」的專屬清單表，屬於已知的體驗改善空間，非功能缺陷。
8. **批次防線覆蓋範圍以本輪已識別的操作為限，且非一體適用**：`cmd_Import`、`cmd_Rebuild`、`cmd_Rescue`、`Mod_Export` 四處剪貼簿或高風險路徑已補齊三層防護；`cmd_Deduplicate` 三迴圈則於V2.2.0改為命令結束後統一存檔一次（見第四部分第9節「批次存檔適用範圍分界原則」、ADR V2-045）。任何新增的逐項處理迴圈，應先核對是否符合分界原則的兩個前提，而非預設套用高頻存檔。
9. **極大量救援（三千張級別以上）時，三層防護不保證零失敗，屬已知、可控的機率性限制**：實測3277張一次性遺失情境時，觀察到失敗原因分為兩類——(a) 聚集型：一次「Automation錯誤」後緊接數十筆「應用程式或物件定義上的錯誤」，研判為COM子系統短暫進入不穩定狀態、需要一段時間自行恢復；(b) 散落型：零星的`Cut`／`Paste`方法失敗，較符合單次剪貼簿資源碰撞。研判已逼近VBA透過COM連續操作系統剪貼簿的實務極限，非單一可修復的程式邏輯錯誤。**決策：不採用批次數量上限機制**（曾考慮「單次最多處理N張、超過留待下輪」的設計，因缺乏可靠依據設定安全值、且會增加程式複雜度而放棄），改以文件告知使用者此限制，失敗項目因單項目隔離機制會維持「等待救援」狀態，重新執行全面排版即可讓系統自動接續處理，極端量級下可能需要重複執行兩三次才能完全收斂，見 README。
10. **「救援夾一鍵重新匯回」已評估並否決（V2.2.0，見ADR V2-043）**：原始構想為複製救援夾圖片至散裝匯入區、刪除原檔、重新走匯入管線歸檔。評估後發現救援夾內圖片本已在《圖片目錄》有完整紀錄，重新匯入會產生目錄表孤兒重複列，技術上不可行；修正方案（比照 `ApplyFileMatch` 邏輯就地正名）技術上可行，但使用情境發生頻率極低（年度一兩次等級），評估不值得投入工程複雜度，暫不實作。此為刻意不做的決策，非遺漏，記錄於此避免未來重新提案討論一次。
11. **同一 session 內長時間不重啟活頁簿，日誌封存機制僅靠開機時機檢查會有空隙（V2.2.0，見ADR V2-041）**：`ArchiveAndTrim` 目前僅於開機流程觸發一次，若使用者長時間不關閉活頁簿、持續在同一session內操作，日誌列數可能在該session內持續累積超過門檻而不會自動封存，需仰賴使用者自行執行 `Alt+F8` 的手動封存入口。
12. **雜湊快取（`m_DictHashCache`）命中來源已查證確認，非玄學（V2.3.0新增）**：`cmd_Rebuild.ICommand_Execute` 每次執行雖會重建全新空字典，但緊接著呼叫的 `BackupCatalogState` 會將目錄表現有每一列（路徑|修改時間|大小 → 雜湊）**直接預先寫入** `m_DictHashCache`，早於掛載主迴圈開始之前——此為刻意的效能設計，讓內容未變動的既有檔案在主迴圈呼叫`GetOrComputeFileHash`時第一次查詢就命中，不需重算MD5。此預先寫入路徑本身不計入`m_HashCacheHit`／`m_HashCacheMiss`統計（僅`GetOrComputeFileHash`內部查詢會計數），故單輪REBUILD的「命中」數字，實際反映的是「目錄表已登記且內容未變的既有檔案數」，「現算」數字則反映「目錄表尚未登記（新匯入或血統未延續）的檔案數」，兩者相加等於本輪實際掃描到的檔案總數。此機制運作正確，非缺陷，此前僅因統計口徑未涵蓋預先寫入路徑而顯得不易解釋。
